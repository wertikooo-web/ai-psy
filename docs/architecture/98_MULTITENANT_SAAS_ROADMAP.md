# 98 — Transcript AI: переход к многопользовательской SaaS-архитектуре

## Статус

Пока **не реализовывать**.

Документ фиксирует архитектурные решения и идеи, к которым необходимо вернуться после завершения MVP.

Текущий приоритет — развитие продукта для одного пользователя.

Многопользовательская архитектура будет следующим крупным этапом.

---

## Цель

Transcript AI должен стать SaaS-продуктом, которым смогут одновременно пользоваться сотни и тысячи психологов.

Каждый пользователь должен работать полностью независимо.

Данные одного психолога никогда не должны быть доступны другому.

---

## Что сейчас считается MVP

До перехода к SaaS необходимо закончить развитие профессионального инструмента:

- транскрипция
- AI-анализ
- Explainable AI (лупы с объяснениями выводов)
- история запросов клиента
- карта случая
- база знаний
- чат по консультации
- экспорт результатов

Архитектура SaaS не должна мешать развитию этих функций.

---

## Основной принцип

Все пользовательские данные должны иметь владельца.

Практически каждая сущность системы должна принадлежать конкретному пользователю:

- клиент
- консультация
- анализ
- чат
- заметки
- материалы
- настройки
- внешняя база знаний

---

## Что должно стать системным (общим для всей платформы)

- встроенная методология анализа
- системные промпты
- внутренние инструкции
- ядро базы знаний
- шаблоны анализа

Эти документы обновляются централизованно и используются всеми пользователями.

---

## Что должно стать пользовательским

Каждый психолог должен иметь собственные:

- клиентов
- консультации и транскрипты
- анализы
- историю запросов
- материалы клиента
- заметки
- внешнюю базу знаний
- пользовательские инструкции для AI
- персональные настройки AI

---

## Необходимая архитектура

Переход на полноценную multi-tenant модель.

Во всех основных сущностях необходимо предусмотреть `user_id` (owner).

Это позволит использовать **Row Level Security** и гарантировать полную изоляцию данных на уровне БД.

```sql
-- Пример RLS-политики
CREATE POLICY "users see own clients" ON clients
  FOR ALL USING (user_id = auth.uid());
```

Подробнее — см. `08_MULTITENANT_SAAS.md`.

---

## История запросов

Запрос клиента должен стать самостоятельной сущностью (`client_requests`), а не строкой в карточке клиента.

Каждая консультация должна быть связана с запросом, который был актуален на момент её проведения.

Это позволит сохранить правильный исторический контекст при смене темы работы.

Детальная архитектура — `05_REQUEST_HISTORY.md`.

---

## История консультаций и динамика случая

Необходимо предусмотреть возможность просматривать историю случая:

- история запросов
- история консультаций
- история анализов
- история чатов
- динамика терапии

Все эти данные должны быть логически связаны и отображаться как единый маршрут клиента.

---

## AI-анализ в SaaS

AI должен работать не только с текущим транскриптом.

В будущем анализ должен учитывать:

- текущий запрос консультации
- историю запросов клиента
- предыдущие консультации
- материалы клиента
- карту случая

При этом необходимо избегать чрезмерного роста prompt. Решение: подготовленный **Analysis Context** — кэшируемый снимок контекста клиента.

---

## Производительность при масштабировании

При росте числа пользователей необходимо предусмотреть:

- кэширование Analysis Context (per-client, инвалидируется при изменениях)
- кэширование Knowledge Base (уже частично реализовано через `compressedTranscript`)
- очереди выполнения AI-задач (Bull/BullMQ или Supabase Edge Functions)
- фоновые процессы (транскрипция, обновление evidence)
- потоковую выдачу результата (SSE streaming)

Повторные вычисления должны максимально исключаться.

---

## Безопасность

До публичного запуска необходимо реализовать:

- авторизацию (Supabase Auth)
- разграничение доступа (RLS на всех таблицах)
- безопасное хранение данных (шифрование чувствительных полей)
- экспорт данных клиента (GDPR)
- удаление данных (полное, не только soft delete)
- аудит действий

Подробнее — `09_SECURITY_AND_PRIVACY.md`.

---

## Масштабируемость

Архитектура должна одинаково хорошо работать для 1, 100 и 1 000 пользователей.

Требования:
- все запросы адресные (через `user_id` или `client_id`)
- нет глобальных SELECT без WHERE
- индексы на всех FK-полях
- никаких in-memory состояний между запросами

---

## Использование ресурсов (тарификация)

В будущем потребуется считать использование AI для тарифных планов:

- количество транскрипций / минуты аудио
- количество AI-анализов
- количество сообщений в AI-чате
- объём пользовательской базы знаний
- объём хранилища (Supabase Storage)

---

## Чеклист перед переходом к SaaS

Провести архитектурный аудит:

- [ ] Все основные таблицы имеют `user_id`
- [ ] RLS-политики покрывают все таблицы
- [ ] Нет серверных запросов с `service_role`, обходящих RLS
- [ ] Чувствительные данные шифруются перед записью
- [ ] Реализован механизм полного удаления данных пользователя
- [ ] Реализован rate limiting per user на AI-вызовы
- [ ] Логирование не содержит персональных данных
- [ ] Протестирована изоляция между тестовыми пользователями

---

## Главное правило

**До завершения MVP не усложнять текущую систему.**

При разработке новых функций помнить о будущей многопользовательской архитектуре, но не внедрять её преждевременно.

Сначала создать действительно сильный профессиональный продукт.

Затем масштабировать до SaaS без полной переработки архитектуры.
